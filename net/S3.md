# S3 uploads

`td-net s3` uploads explicit files; `td-net release upload-s3` publishes a
selected signed deployment. Both use Rust HTTP/TLS and td-primitives
HMAC-SHA256, with AWS Signature Version 4 and signed payload hashes. They
invoke no external uploader and add no external dependency. Uploading is an
operator action, separate from building, signing, and selecting a release.
Neither command deletes remote data or configures buckets, DNS, CDN rules,
lifecycle policies, or access permissions.

## Configuration

Supply an explicit HTTPS endpoint origin, region, bucket, credentials file,
and profile. Requests use path-style `/BUCKET/KEY` URLs. For R2, use the
account's S3 API endpoint (not the public download hostname) and region
`auto`. For AWS, use the bucket's regional S3 endpoint and region. Wrong
regions and redirects fail; authorization is never forwarded to another
origin. Numeric loopback HTTP is allowed for local tests. Ambient proxy
settings and AWS environment credentials are not used.

The credentials file must be an owned regular file, not a symlink, with no
group or other permission bits and at most 64 KiB. Its selected section is:

```ini
[td-releases]
aws_access_key_id = YOUR_ACCESS_KEY_ID
aws_secret_access_key = YOUR_SECRET_ACCESS_KEY
```

An optional `aws_session_token` supports temporary credentials. Duplicate
selected sections/fields, unknown selected fields, and missing credentials
refuse. Other sections are ignored. Profiles contain ASCII letters, digits,
underscores or hyphens. No credential-process, role assumption, metadata
service, or automatic token refresh is supported. Keep credentials outside
the repository; give them access only to the intended bucket. The caller
must protect ancestor directories and prevent concurrent source-file writes.
These tools do not isolate hostile processes sharing the operator's UID.

## Publish a selected release

First stage and promote a local release using [RELEASES.md](RELEASES.md).
Then validate the upload without making any network requests:

```text
net/target/release/td-net release upload-s3 REPOSITORY ROOT system-x86-64 https://ACCOUNT_ID.r2.cloudflarestorage.com auto td-releases /path/to/r2-credentials td-releases --dry-run
```

Remove `--dry-run` to upload. `ROOT` is the public root document, never a
private signing key. The uploader takes the local repository lease, validates
all sequential root documents from epoch one (at most 1024), requires the last
to equal ROOT, checks the selected head and index signatures and signed expiry policy,
and verifies every referenced object and complete payload before contacting
S3. The local publisher's protected-directory rules apply. Dry-run validates
local input and credentials; it does not establish remote access or check
remote state. It may create the local lease file.

Only authenticated references become upload keys, in this order:

1. The selected release's content-addressed objects.
2. Public root documents, in ascending epoch order.
3. The selected signed release index.
4. The selected profile's signed head, after rechecking its signed policy.

Unselected releases, unrelated files, lock files, and private signing keys
are not scanned or uploaded. Root documents are retained remotely. This
command publishes one profile per invocation.

Before uploading, an existing remote head is authenticated using the local
root chain. Older root epochs can advance; the same epoch requires a newer
head and nondecreasing release sequence, with no same-sequence substitution.
Identical heads may be uploaded again. The final write uses `If-Match` with
the observed ETag, or `If-None-Match: *` when absent. A conflicting publisher
cannot be silently overwritten. After a conditional-write conflict, only
exact readback of the intended head counts as success; otherwise rerun after
inspecting the remote state. Failure leaves the previous head in place,
except when a write committed but its reply was lost; that outcome can be
resolved by rerunning. Already uploaded immutable objects remain reusable.

Immutable objects get `Cache-Control: public, max-age=31536000, immutable`;
heads get `Cache-Control: no-store`. Configure CDN rules to honor these
headers, especially for heads. Do not apply bucket-wide age expiration to
shared chunks: a new index can still reference an old object. Use the explicit
[remote collection workflow](#remote-collection) for a
published repository; standalone local GC does not collect remote copies.

## Upload an ISO or detached signature

```text
net/target/release/td-net s3 put /path/to/td-COMMIT.iso iso/td-COMMIT.iso https://ACCOUNT_ID.r2.cloudflarestorage.com auto td-releases /path/to/r2-credentials td-releases --dry-run
```

Remove `--dry-run` to upload. Use a unique versioned key. This command treats
every key as immutable and refuses the reserved `heads`, `roots`, `releases`,
and `objects` namespaces. It does not sign an ISO or establish release trust;
a detached signature is a separate explicit file upload. It never recursively
uploads a directory. Keys are UTF-8, at most 1024 bytes, without controls,
backslashes, empty components, `.` or `..`; reserved bytes are percent-encoded
for signing and transport. Bucket names support 3–63 lowercase letters,
digits and internal hyphens; dotted and specialized bucket names are outside
this initial interface.

## Upload the td website

```text
td-net s3 website www ENDPOINT auto www CREDENTIALS PROFILE --dry-run
```

Remove `--dry-run` to publish. The website command uploads exactly
`style.css`, `assets/favicon.svg`, `assets/td-desktop.jpg`, then `index.html`,
from the supplied directory to those keys at the bucket root. It does not
scan directories or upload the README, launcher, or arbitrary extra files.
Each source must be a nonempty regular file of at most 8 MiB. Final-component
symlinks and any source sharing the credentials file's inode are refused.
All four files are opened and hashed before any network request. Ancestor
directories must be trusted, and source files must not be modified during
publication, as for other uploads.

Unlike `s3 put`, this command deliberately replaces those four fixed keys.
It reads all remote ETags before writing, and uses `If-Match` for existing
objects or `If-None-Match: *` for absent ones. Existing objects need not have
been created by td; replacing one still requires its observed ETag. Reuse
and lost-reply recovery require matching length, SHA-256 upload metadata,
content type and cache policy, trusting the authenticated service's metadata
in the same way as immutable upload reuse. Conflicting writes with different
metadata refuse. Assets are uploaded before the entry page; any asset error
prevents publishing the page. This is not a multi-object transaction, and
concurrent or interrupted uploads can leave a mixture of asset versions.
Serialize deployments and rerun after resolving any failure.

HTML and CSS use their UTF-8 text types, SVG uses `image/svg+xml`, and JPEG
uses `image/jpeg`. All four use `Cache-Control: no-cache` for revalidation of
unversioned paths. Both metadata headers are signed. Nothing is deleted;
there is no cache purge or bucket/routing configuration. [The website
README](../www/README.md) covers root routing and the convenience launcher.

## Retry and bounds

Immutable uploads first compare remote length, `x-amz-meta-sha256`, and cache
policy through HEAD. A matching object is reused; a mismatch or missing
metadata refuses. New files use `If-None-Match: *`. PUT signs the actual
SHA-256 and stores that digest as metadata. Reuse trusts the authenticated
S3 service's stored metadata, not ETag as a content hash; it does not download
and rehash the existing remote body. Release clients independently hash every
object and complete payload. Objects created by another uploader without
these metadata fields require explicit operator reconciliation.

Each request makes at most three attempts on transport errors and HTTP 408,
429, 500, 502, 503 or 504, with bounded backoff and a fresh signature. Other
statuses, redirects included, refuse without following them. Conditional PUT
retries keep the original precondition. Downloads of small comparison metadata
are bounded; a truncated response body fails and can be retried by rerunning.
Diagnostics never include credentials, authorization headers, or server error
bodies. HTTP headers and local paths are not secret inputs.

One command has a one-hour budget across hashing, DNS and network work;
requests also have connection and read/write idle timeouts. Blocking local
filesystem operations have no asynchronous cancellation guarantee. File
uploads stream with a 64-KiB hash buffer and a four-GiB per-file limit. There
is no multipart upload; retry restarts an individual file. Release chunks
are at most 256 KiB, and progress survives interruption at file granularity.
The index and its bounded object plan remain in memory. A changed source
refuses validation or the service's signed-payload check; do not modify files
while uploading.

## Compatibility evidence

Tests use AWS's published GET and PUT SigV4 known answers and a loopback
S3 fixture checking the wire signature and payload. They exercise conditional
writes, lost replies, retries, conflicts, protected credentials, dry-run,
head-last ordering, and authenticated acquisition of the uploaded repository.
These do not substitute for a live R2/AWS compatibility test with the
operator's bucket.

## Signed installer ISOs

[ISO.md](ISO.md) describes `release sign-iso`, `verify-iso`, and
`upload-iso-s3`. The ISO uploader uses the same credentials and transport,
and publishes an immutable detached signature after the image and root.

`release upload-iso-index-s3` publishes the complete explicit ISO catalog and
then replaces `index.html` conditionally, with an HTML content type and
`no-store`. See [the download listing contract](ISO.md#download-listing).
Do not use immutable `s3 put` for the mutable landing page.

## Remote collection

`release gc-s3 REPOSITORY ROOT ENDPOINT REGION BUCKET CREDENTIALS
CREDENTIAL_PROFILE` plans remote collection without deleting anything.
Deletion additionally requires both `--delete --exclusive-publisher`.
The latter acknowledges a maintenance window: stop all other publishers
including those on other hosts, for the entire command.
The repository lease excludes cooperating writers using this same local
repository; it is not a distributed lock. Rechecking discovery cannot make
multi-object S3 operations atomic against a concurrent publisher.

Collection lists the entire remote `releases/` namespace with bounded,
signed ListObjectsV2 requests (1,000 keys and 2 MiB per page, at most
200,000 keys, with continuation-loop and duplicate rejection). Every remote
index must exist byte-for-byte locally, and both remote profile heads must
match their local copies, including absence. Unknown remote history,
missing indexes, corrupt local metadata or changed discovery refuse.
The local repository must therefore be retained and backed up; do not
collect it before remote collection.

The existing local GC reachability rules select candidates: selected
indexes survive indefinitely. Unselected non-expiring indexes survive
30 days after issue plus seven days' grace; legacy indexes survive seven
days after expiry. Every index also survives seven days after non-expiring head promotion or
upload, protecting a recently superseded selection.
The protected local `retention-hold-until` file records that grace before
head replacement or remote upload, even if the upload subsequently fails.
A retry can extend it. Once the repository has non-expiring publication
history, later promotions/uploads keep extending the hold even after a
signed transition back to finite policy; collection always honors an
existing hold, regardless of the currently selected policy. Keep this file with the authoritative publisher
repository; a missing/malformed hold refuses collection of a repository
with non-expiring heads. After restoring or importing publication history,
re-upload the selected head before collection to establish a fresh hold.
Unreachable objects must also be over seven days old locally. Remote candidates must match their local length and recorded
SHA-256 metadata. Discovery and inventory are checked again before deletion;
heads are checked before each deletion. Expired index files are removed
before their unreachable objects. DELETE carries the observed ETag in
If-Match as an additional guard where supported; the exclusive-publisher
requirement remains mandatory, including on R2. Neither metadata comparison
nor ETag substitutes for a download client's cryptographic verification.

With `--delete`, each remote deletion (or confirmed absence) is followed by
removal of that exact local candidate. Both use the same planned set under
one lease: a file crossing the retention boundary during network work stays
on both sides until the next pass. A retry handles remote deletion that
succeeded before a local unlink failed. Do not run standalone local GC on
a published repository: its later cutoff could delete history still remote.
Roots, heads, ISO files, detached ISO signatures and the download page are
never remote collection candidates. Files absent from the local inventory
are not guessed at or deleted. Do not configure a blanket age-based bucket
lifecycle rule: retained releases may still reference old shared chunks.
Deleting an origin object does not purge a CDN copy. Non-expiring signed
bytes can remain authentic in a cache after origin collection; revocation
and client version floors are separate from storage retention.

See [OPERATIONS.md](OPERATIONS.md) for the release cadence and recovery
procedure. Protocol references: [ListObjectsV2](https://docs.aws.amazon.com/AmazonS3/latest/API/API_ListObjectsV2.html)
and [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/).
