# sed — the command language, addressing, options and diagnostics.
#
# td-txt-authored (see spec/README): the vendored GNU sed testsuite drives whole
# SCRIPTS through `sed -f`, so it says little about sed as a PROGRAM — options,
# per-command edge cases, exit statuses, in-place rewriting, what it refuses.
# That is what lives here. Goldens were produced by running each case against
# GNU sed 4.9 under LC_ALL=C.

#### and the rule is the first two BYTES, not the first line
# GNU takes `#n' at the head of the script and stops looking; whatever else is
# on that line is comment. td-txt required a newline or end of script right
# after, so every `#nx' spelling auto-printed -- a WRONG ANSWER rather than a
# refusal, which is the worse kind. (Not the LAST one, as this said at first:
# the `--posix' bracket-suppression xfail is one too.)
## argv: sed "#nx\np"
## stdin:
a
b
## END
## stdout:
a
b
## END
## status: 0

#### but a script arriving through a PIPE never carries it
# GNU decides `#n' with `ftell(prog.file) == 2', which is -1 on a pipe, so a
# `-f -' script off one auto-prints however it starts. td-txt read the file into
# memory and always honoured it -- a divergence that predates the branch for the
# bare `#n' spelling and that the prefix fix above would have WIDENED to every
# `#n...' spelling, so it is closed in the same landing. Found by a reviewer,
# whose sweep used a fifo where mine had used a regular file and so could see it.
## argv: sed -f - data
## file-json data: "a\nb\n"
## stdin:
#nx
p
## END
## stdout:
a
a
b
b
## END
## status: 0

#### and only the FIRST part is asked -- a later pipe cannot revoke it
# The seekability question is about the stream the first two bytes came from,
# so a second `-f' off a pipe leaves the rule alone. Without this the guard
# could be written to let any `-f' clear it and nothing would notice.

## file-json data: "a\nb\n"
## file-json s.sed: "#nx\np\n"
## stdout:
a
b
## END
## status: 0

# GNU's sed escapes are applied to the pattern BEFORE the regex is compiled, so

# WHEN an operand is opened, which is the rule the three cases above turn on.
# GNU opens each only as it reaches it, so a `q' earlier in the script means a
# later operand is never opened and its failure never exists. td-txt read every
# operand up front to resolve `$', so it reported failures GNU never suffers --
# and reported them as SUCCESS, a quit code winning over a status the run should
# never have had. The opening is lazy now, one operand at a time.
#
# The `$' address is what complicates it: answering "is this the last line"
# requires OPENING the next operand, stepping over empty ones, until one has a
# line -- so a script containing a `$' opens operands a script without one does
# not, and reports failures the other never sees. `F' is the cheapest probe,
# naming whatever is open rather than where the current line came from.
#### a q reached BEFORE the last line never opens the next operand

# An operand that OPENS and cannot be READ is a different failure from one that
# would not open: GNU warns about the second and carries on (exit 2) and PANICS on
# the first (`read error on NAME`, exit 4, nothing behind it read). A DIRECTORY is
# the reachable case -- `open(2)` succeeds and the first read fails. Inside the
# lookahead, which is `getc` in GNU, that same failure IS end-of-file: silent, and
# stepped over. `n` and `N` reach input through that lookahead (`test_eof`) before
# they read, so a directory is silent to them and fatal to the cycle that follows.
