# grep — the option surface, exit statuses and diagnostics.
#
# td-txt-authored (see spec/README): the vendored GNU suites cover the REGEX
# engine and assert only an exit status, so everything about grep as a PROGRAM —
# which lines it prints, how it prefixes them, what it exits with, what it
# refuses — lives here. Goldens were produced by running each case against GNU
# grep 3.11 under LC_ALL=C.

#### a NUL byte makes a file binary
## argv: grep -H foo b1
## file-json b1: "foo\x00bar\nbaz\n"
## stdout-json: ""
## status: 0

#### -a treats a binary file as text
## argv: grep -a foo b1
## file-json b1: "foo\x00bar\nbaz\n"
## stdout-json: "foo\x00bar\n"
## status: 0

# A binary buffer has its NULs replaced by the line separator before it is
# searched (GNU's `zap_nuls`), so a NUL ENDS a line. That moves what matches,
# which the counting modes are how you see it: they print no line content, so
# they are not suppressed the way a printing run is. `-a` turns the verdict off
# and the zapping with it, which is what each pair below holds apart.

#### a NUL ends a line, so an anchor matches after it
## argv: grep -c ^y b1
## file-json b1: "x\x00y\n"
## stdout-json: "1\n"
## status: 0

#### -a leaves the NUL in the line, and the anchor does not match
## argv: grep -a -c ^y b1
## file-json b1: "x\x00y\n"
## stdout-json: "0\n"
## status: 1

#### the same for a trailing anchor
## argv: grep -c x$ b1
## file-json b1: "x\x00y\n"
## stdout-json: "1\n"
## status: 0

#### -a, and the trailing anchor does not match either
## argv: grep -a -c x$ b1
## file-json b1: "x\x00y\n"
## stdout-json: "0\n"
## status: 1

#### one line becomes two, so the count is two
## argv: grep -c . b1
## file-json b1: "x\x00y\n"
## stdout-json: "2\n"
## status: 0

#### every NUL of a run becomes a separator, so a run leaves an empty line
## argv: grep -c ^$ b1
## file-json b1: "x\x00\x00y\n"
## stdout-json: "1\n"
## status: 0

#### the NUL itself is gone, so a pattern holding one cannot match
## argv: grep -c -f pat b1
## file-json pat: "\x00\n"
## file-json b1: "x\x00y\n"
## stdout-json: "0\n"
## status: 1

#### -a, and the pattern holding a NUL matches
## argv: grep -a -c -f pat b1
## file-json pat: "\x00\n"
## file-json b1: "x\x00y\n"
## stdout-json: "1\n"
## status: 0

#### -z reaches no verdict at all, so nothing is zapped
## argv: grep -z -c ^a b1
## file-json b1: "\x00a\n"
## stdout-json: "1\n"
## status: 0

# of it (grep/src/dfasearch.c:301-325,479). Which span to PRINT is a different
# reading: the retry loop at dfasearch.c:528-567, which shrinks a non-word-bounded
# match at the same start and otherwise advances the start by one.
#
# So `-o -w '..\?'` on `a b c` prints `a` and `c` and never `b`, though every one

# applied from the LINE start, so under `-o` it closes over the match as the line
# is consumed and shrinking stops working. The fourth case is the contrast: where
# no span needs shrinking every start is printed.

# Two properties of the shrink that no case above reaches, each a shape where
# getting it wrong INVENTS a span rather than losing one. Both need a THIRD
# alternative matching later in the line, because a line the wrapped dfa does not
# select never reaches the `-o` loop at all and the decision stays invisible --
# which is how these two were first written, and they pinned nothing.
#
# GNU shrinks with `not_eol` set, so `$` does not hold at the cut: `a\.` matches
# the `a.` of `a.b`, the `b` disqualifies it, and the only shorter span left is the

# A KNOWN GAP, listed xfail in expectations.txt rather than fixed: the retry loop
# above runs over GNU's whole pattern LIST at once, not over one pattern at a
# time. Without a backreference `dc->pcount` stays 1 and GEAcompile hands the
# newline-joined list to glibc as a SINGLE regex (dfasearch.c:236-295), so
# `re_search` is leftmost-longest over the union and the shrink walks down from
# the union's span. td-txt compiles one regex per pattern, runs one loop each and
# takes the leftmost-longest of the answers, which is a different function rather
# than an optimisation of the same one -- a start whose union span cannot be
# shrunk into a word can still be word-bounded for one pattern alone.
#
# So `-e '..\?' -e '[a-z]\+'` over `a.b aa` prints `b` here and not in GNU: the
# union's greedy span at that start is `.b`, every shrink window from it is
# closed, and GNU slides past. SELECTION is unaffected and agrees -- the wrapped
# dfa over the union answers the same question as the per-pattern scan does --
# which the last two cases pin. Closing it needs the pattern list compiled as one
# regex, which is its own increment and reaches well past `-w`.

# An unusable brace -- one that CLOSES on content no interval can have, `{}` and
# `{2,1}` -- is the text it is while there is nothing to repeat, and the complaint
# about its content once there is. grep's ERE carries that "nothing to repeat"
# state past an anchor, an assertion, a dropped operator and a brace it could not
# read as an interval, so `^{}`, `\b{}` and `{{}` all compile where `a{}` and
# `{}{}` do not. A VALID interval ends the state even though it may be dropped,
# which is the asymmetry no reading predicts: `^{2}{}` is the error `^{}` is not.

# ---- POSIXLY_CORRECT: the first operand ends the options ------------------

#### POSIXLY_CORRECT stops the permutation, so a flag after the first operand is a FILE
# GNU permutes by default: it collects options wherever they sit, so `grep a h -n'
# numbers its output. POSIX says the first operand ends the options, and setting
# POSIXLY_CORRECT is what asks GNU for that -- `-n' is then a filename that is not
# there, which is a diagnostic and exit 2 rather than a numbered line.

## file h:

# glibc reads a class name there without ever looking it up, and abandons the
# construct at the first byte outside `a'..`y'. `z' is outside -- the bound is
# exclusive -- so the `:' is re-read as an ordinary byte and the set ends at
# the FIRST `]', leaving the second one a literal the name must end with. So
# `a' is passed over and `a]' is selected. The second file is the whole point:
# over `a' alone, a pattern simply given up would answer the same.
## argv: grep -r --include=[a[:zz:]] -l hit t
## file t/a:
hit
## END
## file t/a]:
hit
## END
## stdout-json: "t/a]\n"
## stderr-json: ""
## status: 0

#### the same backoff with no name at all closes the set instead
# One byte shorter and the `]' the class name never reached is the set's own.
## argv: grep -r --include=[a[:] -l hit t
## file t/a:
hit
## END
## stdout-json: "t/a\n"
## stderr-json: ""
## status: 0

#### and a set that never closes still falls back to a literal `['
# The fallback is not the scan's alone: this matches an item, runs off the end
# of the pattern inside the walk, and still re-reads the `[' as an ordinary
# byte -- so `*[[' selects a name ending in `[['.
## argv: grep -r --include=*[[ -l hit t
## file t/x[[:
hit
## END
## stdout-json: "t/x[[\n"
## stderr-json: ""
## status: 0

#### whether `^' negates a set is the ENVIRONMENT's answer, not the pattern's
# glibc reads POSIXLY_CORRECT, and under it a leading `^' is an ordinary member
# rather than a negation. So `[^^]' is "not a caret" here and selects nothing.
## argv: grep -r --include=[^^] -l hit t
## file t/^:
hit
## END
## stdout-json: ""
## stderr-json: ""
## status: 1

#### and the same glob over the same file selects it under POSIXLY_CORRECT
# The pair is the assertion: one run cannot show that the environment decides.
## argv: grep -r --include=[^^] -l hit t
## env POSIXLY_CORRECT: 1
## file t/^:
hit
## END
## stdout-json: "t/^\n"
## stderr-json: ""
## status: 0

#### `!' negates either way, which is what makes the pair above about `^'
## argv: grep -r --include=[!a] -l hit t
## env POSIXLY_CORRECT: 1
## file t/^:
hit
## END
## stdout-json: "t/^\n"
## stderr-json: ""
## status: 0

#### ...and without it, which is the half that makes "either way" true
## argv: grep -r --include=[!a] -l hit t
## file t/^:
hit
## END
## stdout-json: "t/^\n"
## stderr-json: ""
## status: 0

#### a `-]' after a COLLATING element is a range, so the element is not an item
# glibc asks "is this a range?" one way after `[.x.]' and another after a plain
# byte, and the two spellings differ by exactly this case. Being a range skips
# the item test, and then there is no high end to use, so `a' is not selected.
## argv: grep -r --include=[[.a.]-] -l hit d
## file d/a:
hit
## END
## stdout-json: ""
## stderr-json: ""
## status: 1

#### where the same shape after a plain byte leaves the byte an item
# The control the case above needs: one character shorter and `a' is selected.
## argv: grep -r --include=[a-] -l hit d
## file d/a:
hit
## END
## stdout-json: "d/a\n"
## stderr-json: ""
## status: 0

#### and an equivalence class is not a collating element for this purpose
## argv: grep -r --include=[[=a=]-] -l hit d
## file d/a:
hit
## END
## stdout-json: "d/a\n"
## stderr-json: ""
## status: 0
