# Where td-txt deliberately does NOT do what GNU does.
#
# Every other case file in this corpus takes its goldens from GNU grep 3.11 /
# GNU sed 4.9 (see spec/README). These do not: each one pins a behavior td-txt
# chooses differently ON PURPOSE, so the choice is a test rather than a comment
# somebody can quietly delete. A case here that starts failing means td-txt
# drifted from a decision, not from upstream.
#
# Most cases here are refusals and fail CLOSED — a diagnosed error and a non-zero
# status, never a silent no-op — so a script written for GNU cannot mistake a
# refusal for success. Several are not refusals but different ANSWERS (the anchor
# inside a repeated group, the `-r` walk ORDER after it, and the permuted `-NUM`
# family at the end); they are here because the reason is the same — a decision,
# not a gap — and a differing answer needs pinning more than a refusal does,
# since nothing about it is self-announcing. One differs in KIND rather than in
# value: a permuted `-NUM` past the digit cap is a refusal here and a wait that
# never ends there. The walk order differs in what a GOLDEN can be: the other
# two reject an answer GNU gives consistently, where GNU has no stable answer
# here to capture at all.

#### grep refuses -u, the option that exists only to modify -b
# GNU takes `-u`/`--unix-byte-offsets`, warns that it is obsolete, and then
# does nothing with it: `grep -ub` prints exactly what `grep -b` prints. It
# dates from the MS-DOS ports, where a text-mode read and the file on disk
# disagreed about CRLF and `-b` needed telling which it meant. On a POSIX
# system the two never disagree, so there is no second answer for it to
# select. Recorded here because it is the one option whose whole subject is
# `-b`, and `-b` is now served -- so a reader looking for it should find why
# it is not, rather than nothing.
## argv: grep -ub a
## stdin:
a
## END
## stdout-json: ""
## status: 2
## stderr-contains: invalid option -- 'u'

#### grep refuses -I, whose effect a caller reads in the STATUS
# -I is --binary-files=without-match: a binary file stops counting as a match.
# Not retroactively -- matches already emitted before the binary verdict trips
# are still printed -- but from the verdict onward, and the STATUS is withheld.
# td-txt serves the behaviour of the other two modes: the default (`binary file
# matches' on stderr) and `text', which is what -a and --text do. So the
# machinery exists and this refusal is the third mode. That is what makes
# ignoring it the tempting mistake, and it would be wrong twice over: on a
# matching binary file GNU's `grep -I hit b' exits 1 where the default does 0,
# AND it prints nothing where the default writes `b: binary file matches'. The
# status is the half a script branches on, which is why it leads here, but the
# diagnostic goes too.
#
# `--binary-files=' is SERVED for its other two values, so what is refused
# here is the VALUE and not the option: `=text' and `=binary' are spellings of
# `-a'/`--text' and of the default, and both answer as GNU does. Only
# `without-match' is unimplemented, and it says so -- a known type this build
# does not serve, which is not what GNU's message for an unknown one says.
## argv: grep -I a
## stdin:
a
## END
## stdout-json: ""
## status: 2
## stderr-contains: invalid option -- 'I'

#### and --binary-files=without-match, the one value of it not served
# The operand is BINARY because that is the only shape where the value does
# anything: GNU withholds the match and exits 1, where the default exits 0

# the diagnostic names the TYPE rather than the option, the option being

## argv: grep --binary-files=without-match hit b

## stdout-json: ""

#### grep refuses -T rather than dropping an alignment that WAS asked for

#### grep -r sorts each directory's entries, where GNU takes the kernel's order
# GNU passes fts NO comparison function (grep.c:1868), so its `-r` listing is
# whatever readdir returns -- a property of the filesystem rather than of grep,
# and past 10000 entries in one directory gnulib's fts sorts by INODE instead
# (grep 3.11's lib/fts.c:150,1568,1624; the boundary is measured at 10001).
# Neither is reproducible across checkouts, and a recipe that greps a tree has
# to produce the same bytes on every build, so td-txt sorts. This golden is
# td-txt's own for a reason the other non-refusals do NOT share: theirs reject
# an answer GNU gives consistently, where GNU has none here to capture.
#
# Per-DIRECTORY, and the tree is shaped to tell that from a sort of the PATHS:
# `-` and `.` sort below `/`, so a path sort gives `t/mid-z t/mid.a t/mid/aaa`

#### and --file, its long spelling, which is a SECOND call site
# `-f' and `--file' read their script through one function but wrap its failure
# at two call sites, and the corpus pairs them elsewhere for exactly that reason
# (sed-cli.test.txt, `an unreadable --file script is the same runtime failure as
# -f'). A review drifted the long arm ALONE and the whole gate stayed green
# while the two spellings of one option disagreed.
## argv: sed --file=D
## file-json D/keep: ""
## stdin-json: "a\nb\n"
## stdout-json: ""
## stderr-json: "sed: read error on D: Is a directory\n"
## status: 4

#### --exclude-from reads its file ONCE, where GNU reads it twice and loses it
# GNU keeps TWO exclude lists -- one for names the walk produced, one for names
# written on the command line -- and `--exclude-from' is added to both by
# reading the file once per list (grep.c's `for (int cmd = 0; cmd < 2; cmd++)').
# A regular file is opened twice and both lists get the globs. A NON-SEEKABLE
# source is not: `-', `/dev/stdin', a fifo and a process substitution are all
# drained by the FIRST read, so GNU's command-line list ends up EMPTY and
# `grep --exclude-from=- PAT operand' does not exclude the operand it was just
# told to. Measured: with `a.c' on stdin, GNU prints d/a.c and exits 0, while
# the walked half of the same run (`-r ... d') DOES exclude it -- so the option
# half-works rather than failing.
#
# td-txt keeps one list and reads the file once, so both halves see the globs.
# This is a deliberate divergence and not an oversight: reproducing it would
# mean reading the argument twice on purpose so that one of the two answers
# could come out empty, which is an artifact of GNU's data structure rather
# than a behavior anything could depend on deliberately.
## argv: grep --exclude-from=- -l hit d/a.c
## file d/a.c:
hit
## END
## stdin:
a.c
## END
## stdout-json: ""
## stderr-json: ""
## status: 1

#### colouring DEGRADES rather than failing when the matcher runs out of budget
# td-txt's matcher has a step budget; GNU's does not. A pattern that exhausts
# it while LOCATING spans for `--color' would, taking the same route `-o'
# takes, refuse the whole run -- and a search that had already selected this
# line would exit 2 with no output at all. That trade is wrong for a
# decoration, so the walk stops and the record prints unpainted instead.
# GNU paints it. Bytes and STATUS agree; only the escapes differ, which is
# the one direction this divergence is allowed to run. `-o' keeps the refusal,
# because there the span IS the output rather than a highlight on it.
## argv: grep --color=always -w -e key -e '[^:]*.*a\(ab\)*a*' f

## stdout-json: "key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val key=val \n"
## stderr-json: ""
## status: 0


#### and a multi-pattern span differs from GNU's union, which colour now shows
# td-txt locates spans per PATTERN and takes the best; GNU matches the union
# of the alternation. On `a.b aa' with `-w' GNU colours `a' and `aa' only,
# while td-txt also colours `b'. The gap is the matcher's and predates this
# landing -- `-o' already showed it -- but whole-line output agreed until
# there were escapes to place, so it is recorded again here at the point it
# became visible. Selection, count and status are unaffected: the same run
# without `--color' matches GNU byte for byte.
## argv: grep --color=always -w -e '..\?' -e '[a-z]\+' f
## env GREP_COLORS: ms=31:sl=07
## file-json f: "a.b aa\n"
## stdout-json: "\u001b[07m\u001b[K\u001b[31m\u001b[Ka\u001b[m\u001b[K\u001b[07m\u001b[K.\u001b[31m\u001b[Kb\u001b[m\u001b[K\u001b[07m\u001b[K \u001b[31m\u001b[Kaa\u001b[m\u001b[K\n"
## stderr-json: ""
## status: 0


#### and an anchored pattern paints nothing where GNU paints an inner match
# The third of the same family, and the same one direction: bytes and status
# agree, only escapes differ. GNU's painting pass looks for the pattern
# UNANCHORED even under `-x', so on a context line `aaa' it paints the `aa'
# inside; td-txt asks its span search the anchored question and is told there
# is no match, so it paints none. Reachable only where a line prints WITHOUT
# having been selected by the pattern -- here the trailing context `-m1 -A2'
# leaves after the count is spent, under `-v'. Without `--color' the two agree
# byte for byte, which is why this surfaced only once there were escapes to
# place.
## argv: grep --color=always -m1 -A2 -v -x aa gx
## env GREP_COLORS: ms=31:mc=34
## file-json gx: "aaa\nbbb\naaa\nccc\naaa\n"
## stdout-json: "aaa\nbbb\naaa\n"
## stderr-json: ""
## status: 0
