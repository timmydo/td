# Where td-txt deliberately does NOT do what GNU does.
#
# Every other case file in this corpus takes its goldens from GNU grep 3.11 /
# GNU sed 4.9 (see spec/README). These do not: each one pins a behavior td-txt
# chooses differently ON PURPOSE, so the choice is a test rather than a comment
# somebody can quietly delete. A case here that starts failing means td-txt
# drifted from a decision, not from upstream.
#
# Most cases here are refusals and fail CLOSED — a diagnosed error and a non-zero
# status, never a silent no-op — so a script written for GNU cannot mistake a
# refusal for success. Several are not refusals but different ANSWERS (the anchor
# inside a repeated group, and the permuted `-NUM` family at the end); they are
# here because the reason is the same — a decision, not a gap — and a differing
# answer needs pinning more than a refusal does, since nothing about it is
# self-announcing. One differs in KIND rather than in value: a permuted `-NUM`
# past the digit cap is a refusal here and a wait that never ends there.

#### sed refuses the e command, which would need a shell
# GNU sed's `e` runs its argument through /bin/sh. td-txt is a static binary
# with an empty runtime closure; a sed that spawns a shell puts the dependency
# td is removing right back, and on the image would reach for the /bin/sh
# td-sh is still replacing.
## argv: sed '1e echo hi'
## stdin:
a
## END
## stdout-json: ""
## status: 1
## stderr-contains: the `e' command is not supported

#### sed refuses the s///e flag for the same reason
## argv: sed s/a/b/e
## stdin:
a
## END
## stdout-json: ""
## status: 1
## stderr-contains: the `e' flag is not supported

#### grep refuses -u, the option that exists only to modify -b
# GNU takes `-u`/`--unix-byte-offsets`, warns that it is obsolete, and then
# does nothing with it: `grep -ub` prints exactly what `grep -b` prints. It
# dates from the MS-DOS ports, where a text-mode read and the file on disk
# disagreed about CRLF and `-b` needed telling which it meant. On a POSIX
# system the two never disagree, so there is no second answer for it to
# select. Recorded here because it is the one option whose whole subject is
# `-b`, and `-b` is now served -- so a reader looking for it should find why
# it is not, rather than nothing.
## argv: grep -ub a
## stdin:
a
## END
## stdout-json: ""
## status: 2
## stderr-contains: invalid option -- 'u'

#### grep refuses -P rather than pretending to have PCRE
# GNU grep's -P switches to a whole second regex engine (PCRE). td-txt carries
# one POSIX engine; accepting -P and quietly running POSIX semantics would
# silently change what a script matches.
## argv: grep -P a
## stdin:
a
## END
## stdout-json: ""
## status: 2
## stderr-contains: invalid option -- 'P'

#### sed refuses --debug rather than accepting it as a no-op
# GNU's --debug prints an annotated dump of the program and each cycle's state.
# td-txt does not implement it. Accepting it silently would fail OPEN: a script
# run for its debug output would produce none and still exit 0.
## argv: sed --debug p
## stdin:
a
## END
## stdout-json: ""
## status: 1
## stderr-contains: unsupported option -- 'debug'

#### sed refuses --follow-symlinks rather than accepting it as a no-op
# It changes which file -i rewrites. WITHOUT it — td-txt's only behavior, and
# GNU's default — a symlink operand is REPLACED by a regular file and its target
# is untouched; WITH it GNU resolves the link and rewrites the target instead.
# Accepting it as a no-op would silently edit the wrong file, so it is refused.
# `sed_in_place_replaces_a_symlink_rather_than_following_it` pins the default a
# case file cannot express (the harness materializes no symlinks).
## argv: sed --follow-symlinks -i s/a/b/ f
## file f:
a
## END
## stdout-json: ""
## status: 1
## stderr-contains: unsupported option -- 'follow-symlinks'

# GNU prints `grep (GNU grep) 3.11' and a copyright block. td-txt is not GNU

#### an anchor inside a repeated group keeps leftmost-longest, where GNU reports empty
# `^` inside a subexpression is a GNU extension; POSIX does not define an anchor
# there at all, and GNU's own answer here is an artifact of how it compiles one
# inside a `\+`. On `a]` GNU selects the EMPTY span at the start; td-txt selects
# the longer `a`, which is what leftmost-longest says. Pinned rather than chased:
# matching GNU would mean special-casing an undefined construct.
## argv: grep -o -e '\(^[a-c]\{0,2\}\)\+'
## stdin-json: "a]\n"
## stdout:
a
## END
## stderr-json: ""
## status: 0

#### a context count too big to wait for is answered, not waited on
# Exactly AT -NUM's cap of 21 significant digits (the five leading zeros are not
# among them), so the count is accepted -- and GNU then walks its before-count
# down in a loop whose cost is linear in the NUMBER, so it does not return
# (still running after 20s), which is why this golden is td-txt's own and not
# captured from it. td-txt's before-window is a ring that GROWS as lines arrive
# and is indexed arithmetically, so the count costs what the FILE holds rather
# than what the NUMBER says, and the answer is the one GNU is computing: every
# line, the context covering the file. Reserving the count up front is what an
# earlier draft of the streaming reader did, and it aborted here before reading
# a line. One more digit is the refusal two cases up in grep-cli.
## argv: grep -00000111111111111111111111 -n a h
## file h:
a
b
b
b
b
a
## END
## stdout-json: "1:a\n2-b\n3-b\n4-b\n5-b\n6:a\n"
## stderr-json: ""
## status: 0

#### a permuted -NUM keeps every digit, where GNU drops the first
# GNU's `-NUM' loses its FIRST digit when the run is the first option element
# after an operand: `grep MATCH f -12 -A0' takes two lines of context there and
# twelve here, and `-123' is 23 rather than 123. It is positional and nothing
# else: the FIRST element of every option block that follows an operand loses
# a digit, so `-12 MATCH f' and `MATCH f -A0 -12' keep the whole run while
# `MATCH -A0 f -12' does not, and it recurs per block rather than firing once.
# Two runs are safe only while ADJACENT. That shape comes from
# getopt's permutation bookkeeping resetting the digit buffer once, mid-run;
# no reading of the option makes a count mean one thing after a filename and
# another before it. Not reproduced: a count that silently loses a digit by
# position is not a behaviour a caller can want, and every position agrees here.

#### sed refuses a `-f' script that is a DIRECTORY
# GNU opens it, reads nothing, and runs the EMPTY program that results --
# auto-printing at exit 0. The mechanism is that `inchar' guards on `feof' and
# never asks `ferror' (compile.c:244), so a `getc' that FAILS simply ends the
# script. Matching that would mean `sed -f "$conf" f' with $conf a directory
# silently applies no edits, passes its input through and exits 0, which no
# caller can tell from success -- a read that FAILED is not the same thing as a
# script that was empty, and the shape that really is empty is pinned below and
# agrees with GNU. The message names the call that FAILED: the open succeeded
# here and the read did not, so this is `read error on %s' (utils.c:240), which
# is what td-txt already prints for an OPERAND and for `r'/`R' on the very same
# errno. `couldn't open file' is reserved for an open that really failed, and
# `-f NOPE' still says it -- byte for byte with GNU, which is the half of this
# path that does agree. A DIRECTORY is only the reachable member of the class:
# any read that fails on an opened script does this, and `sed -f /proc/self/mem'
# is the same divergence with EIO.
